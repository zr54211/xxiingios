# iOS-слой

Состояние: **готово, проверено на устройстве** (iPhone XS, iOS 18, платформа 8.3.27).
Полный UX-паритет с Android: камера 1080p, уголки-сопровождение со скруглёнными
изломами, фонарик, tap-to-focus, автозакрытие с паузой 0.5 с (цветной стоп-кадр
кадра декода, событие в 1С после паузы).

## Механизм подключения статической ВК (главное отличие от Android)

- ВК статически линкуется в исполняемый файл приложения; проект платформы
  собирается с `-all_load`, библиотека въезжает целиком.
- Загрузчик ВК **не использует dlsym**: компонента обязана сама
  зарегистрироваться при загрузке процесса вызовом
  `RegisterLibrary(имя, 0, таблица)` из статического конструктора
  (см. `core/exports.cpp`, блок `__APPLE__`; прототип — шаблон templateMobile
  из комплекта «Технология создания внешних компонент»).
- Точки входа на iOS **внутренние** (анонимный namespace): в бинарнике нет
  глобальных `_GetClassObject` и т.п., загрузчик получает их только из таблицы
  `RegisterLibrary`. Так устроен шаблон templateMobile; CI `ios-lib.yml` падает,
  если точки входа снова окажутся глобальными.
- Почему это обязательно (ВК 0.2.1, 2026-10-06): все ВК приложения линкуются
  в один исполняемый файл, и одноимённые глобальные точки входа разных ВК
  конфликтуют. До 0.2.1 наши были глобальными `weak`, и сильные символы
  другой ВК (MxlBmpNative в конфигурации BIS) молча их подменили: компонента
  подключалась, но `Новый("AddIn....")` падал с «Тип не определен».
  Несколько Native API ВК в одном приложении уживаются, если все они следуют
  этому правилу (проверено: сканер + MxlBmpNative + POS_Printer).

## Архитектура (`IosScanner.mm`)

- `BSZScanner` — сессия `AVCaptureSession` (1920x1080, 420f FullRange),
  кадры в ориентации сенсора без CPU-поворота; Y-плоскость →
  `bsz::DecodeLuminanceEx`; маппинг точек кода в координаты экрана через
  `AVCaptureVideoPreviewLayer pointForCaptureDevicePointOfInterest`.
- Оверлей живёт в **собственном UIWindow** (`UIWindowLevelAlert + 1`) — формы
  1С, открываемые сразу после доставки штрихкода, его не перекрывают
  (паритет с отдельной Activity Android).
- `BSZMarkerView` — CADisplayLink-анимация уголков (lerp 0.35), скругление
  изломов дугой 9 pt (паритет с `CornerPathEffect` Android).
- Автозакрытие: при распознавании превью замораживается
  (`connection.enabled = NO`), поверх кладётся цветной стоп-кадр кадра декода
  (BGRA собирается вручную из YUV — CoreImage намеренно не используется:
  неизвестно, линкует ли его приложение платформы), пауза 0.5 с, **затем**
  `ScanResult` и закрытие (событие после паузы — иначе BSL-обработка штрихкода
  заняла бы главный поток и остановила анимацию рамки). Внешний `StopScanning`
  в это окно **не обрывает** паузу (касса закрывает сканер сразу после
  обработки штрихкода — экран дозакрывается сам, диалоги показываются после).
- Ошибки пишутся `NSLog` с префиксом `BarcodeScannerZXing`; смотреть с Windows —
  `pymobiledevice3 syslog live` или `idevicesyslog`.

## Автофокус: каскад wide → телефото → контрастный AF

Встречаются iPhone (подтверждено на iPhone XS), у которых у wide-модуля мёртв
замкнутый контур автофокуса в video-сессиях: механика линзы исправна (точно
встаёт на любую позицию `setFocusModeLockedWithLensPosition`), но контроллер
делает лишь слепые прогоны и на резкость не сходится; штатная «Камера» на таких
устройствах фокусируется телефото-модулем. Важно: «линза движется» — НЕ критерий
живости AF, живость определяется только по достигнутой резкости кадра.

Каскад в `BSZScanner` (машина состояний на `_videoQueue`):

1. **Wide, штатный CAF.** Старт всегда на wide; фокус не настраивается — камера
   остаётся в заводском continuous AF (разовый AutoFocus-«пинок» на полуживом
   контроллере убивает CAF насовсем).
2. **Наблюдение 4 с.** Каждый кадр меряется резкость центра (`SharpnessOfCenter`,
   средний горизонтальный градиент центральной четверти; «мыло» ~2, фокус ≥5).
   Если порог 5.0 ни разу не взят — контур признан мёртвым, вход сессии горячо
   подменяется на **телефото** (`beginConfiguration`/`removeInput`/`addInput`;
   у телефото свой привод и свой контур AF). Ограничения телефото-режима:
   ближний предел фокуса ~30 см, фонарик недоступен (torch — у wide-модуля).
3. **Контрастный AF** — если телефото нет или и он не дал резкости: собственный
   перебор линзы. Грубый проход 0→1 «лесенкой» 0.033 раз в 2 кадра (частые
   команды позиции обрывают ramp драйвера линзы), замер каждого кадра — против
   **фактической** `lensPosition` трёхкадровой давности (лаг конвейера камеры);
   точная доводка ±0.05 шагом 0.012; лок с медианным сглаживанием 3 кадров,
   локальный рефокус ±0.15 при устойчивом падении резкости, полный re-sweep
   на бесфактурной сцене. Тап при активном контрастном AF — полный повторный проход.

Вердикты («нужен телефото», «AF мёртв») — статики на сеанс приложения:
повторные открытия сканера стартуют сразу в правильном режиме, без паузы
наблюдения. Нюанс: на дальней фактурной сцене припаркованная линза резка и без
AF — вердикт «жив» может быть ложноположительным; для кассового сценария
(код подносят близко, там мыло) некритично.

Диагностика чужого устройства — ветка **`test-contrast-af`**: двухпальцевый тап
циклит режимы cascade / contrast-wide / contrast-tele (плашка-индикатор на
экране, подробные логи `af:*` в syslog); CI на ветке запускается вручную:
`gh workflow run ios-lib.yml --ref test-contrast-af`.

## Сборка (без Mac)

GitHub Actions `.github/workflows/ios-lib.yml` (репо `zr54211/xxiingios`,
раннер macos-15/Xcode 16 — libc++ Xcode 15 не собирает C++20-код zxing-cpp):
CMake Ninja `-DCMAKE_SYSTEM_NAME=iOS`, arm64, target 11.0 → `libtool -static`
склеивает с zxing-cpp → артефакт `libBarcodeScannerZXing-ios-arm64`.
Готовый `.a` кладётся в `iOS/` внутри zip-макета (`arch="universal"`
в manifest.xml — сборщик 1С кладёт iOS-ВК только в `iOS\Universal\`).
